# 自动歌词 v2 方案调研

日期：2026-10-28。需求见 `docs/requirements-auto-lyrics.md`。原型和原始数据在仓库外的原型目录 `$LYRICS_PROTO/`（不随仓库分发）：`align/`（对齐）、`fp/`（指纹）、`survey/`（服务端、B 站、原曲来源）。三个原型由 Pi（Gemini 3.8 flash-high / Grok 4.7）实现，下文结论经过 Claude 复跑和抽查；凡未核实的地方都单独标出。

## 1. 结论

推荐**以客户端纯 JS 对齐为主路**：用 chroma CENS 特征和 GapDTW 对齐，参考音频从 B 站搜原曲搬运视频。**音频指纹**作为 MV/原曲搬运的快速识别与定位辅助，**共享缓存**以后作为可选加速层再加。

- 计算不再是瓶颈：Mac M1 Pro 上纯 JS 对一首单曲做完特征提取、粗对齐、逐行对齐共 0.64 s，冷启动 1.28 s，峰值 RSS 133 MB，零依赖。
- 第一首歌出歌词的瓶颈变成了识别、搜原曲、下载两段音频和解码。这几步在应用里还没有端到端实测过。
- **还没验证、并且最可能不达标的是真实 Live 的逐行精度**：合成样本全部达标，但合成样本是原曲的近似拷贝，比真实 Live 容易得多；真实 Live 上发现了重复段落只能对齐一次的问题（§3.3）。在定实施计划之前，要先补上 Live 银标，并修复重复段的处理。

## 2. 三条路对比

| 维度 | ① 客户端 JS 对齐（chroma CENS + GapDTW） | ② 音频指纹（landmark） | ③ 服务端共享缓存 |
|---|---|---|---|
| 解决什么 | 把原曲的行时间映射到视频时间轴：粗对齐 + 逐行，能处理 Live 和串烧 | 认出是哪条原曲、对应原曲的哪一秒；只对近似拷贝有效 | 第一个人算完，后来的人直接拿结果；还能共享用户修正 |
| 能否单独成立 | 能 | 不能：Live 上全部失效 | 不能：总得有人先算 |
| 首次耗时（计算部分，M1 Pro） | 粗对齐 14 ms；整首 0.64 s；309 s 的 Live 1.09 s；冷启动 1.28 s（已复跑） | 建索引约 0.44 s/首；10 s 片段查询约 40 ms，变速搜索时约 130 ms | 命中时只有一次 HTTP 请求，大约 0.1–0.3 s（推测，未实测） |
| 首次耗时（端到端） | 未实测。估算为识别 + 搜原曲（各一次请求）+ 下载原曲和视频音频（各约 3–4 MB）+ 解码（ffmpeg 约 0.25 s）+ 计算 1 s ≈ 3–6 s（推测） | 同左，并且仍然需要原曲 | 命中时 < 1 s（推测）；没命中就退回 ① |
| 后续耗时 | 本地缓存命中，接近 0 | 同左 | 同左 |
| 精度：合成金标 | 24 个样本：中位数 106 ms，P90 208 ms，覆盖率 98.5%，MC 误显示 0 行；串烧起止误差中位数 0.03 s、P90 2.0 s（已复跑） | 原曲片段：24/24 认对，定位误差 ≤ 0.014 s；±3% 变速要改用对数频率哈希 | 不涉及 |
| 精度：真实 Live | **未证实**。粗偏移与 ② 独立结果一致（3/4）。逐行：sora 与 Qwen 粗参考（约 ±3 s）比，17 行中 12 行在 3 s 内，开头重复唱的 3 行差 43 s | 不可用：4 个 Live 的每个查询窗都被拒绝；AcoustID 对 Live 返回 0 条 | 不涉及 |
| 体积 | 原型 805 行 JS，0 依赖 | 约 12 KB JS；每首索引约 0.7 MB（运行时生成，不进安装包） | 客户端只多一个 fetch |
| 跨平台 | 纯 JS，Mac 和 Linux 实测；Windows 未测，预期没有问题 | 同左 | 不涉及；但要注意中国大陆可达性 |
| 运营成本 | 0 | 0。AcoustID 在线 API 免费层仅限非商用，不采用 | Cloudflare 免费层下 1k DAU 够用，10k DAU 会超（Workers 每天 10 万次请求）；需要自定义域名 |
| 主要风险 | 真实 Live 的逐行精度；重复段；参考音频来源 | 大曲库下的误识别没测 | workers.dev 在大陆不可用（转述，未实测）；匿名上传可能被投毒 |

## 3. 关键发现

### 3.1 参考音频（原曲）

| 来源 | 实测 |
|---|---|
| 网易云匿名 | GBC 3 首都是 VIP 歌，`/api/song/enhance/player/url` 返回 `url: null`，外链 302 到 404。不可用 |
| B 站搜原曲 | 按“时长差 ≤ 2 s + 标题关键词（原曲、CD、罗马音、扒谱）− Live/翻唱”打分，3 首都挑出了 CD 音源搬运，例如 `BV1Vb421q7ro`，与网易云时长相差 0 s。官方 MV 片头片尾多出 30–50 s，可以作为备选，靠粗对齐吸收偏移 |

结论：参考音频以 B 站搜索为主。B 站接口要带 wbi 签名；从海外 IP 请求会把 `BV1dy75z8Enu` 这类视频误报成 -404，但从 Mac 请求正常。调研结论“已下架”是错的，已经更正。

### 3.2 B 站元数据（匿名可取）

- view（分 P、简介、tid）和 tag 都能取到。章节 view_points 在 12 个案例里全是空的，置顶评论里也没有时间轴歌单。歌单来源主要还得靠分 P 标题、简介和 AI。
- 字幕：走 `/x/v2/dm/view`，`lan` 以 `ai-` 开头的是 AI 字幕。12 个案例里只有 1 个有 AI 字幕。

### 3.3 真实 Live 的问题（Claude 复核）

- sora Live（`BV1QhieYjEY2`）：原型把第 0–2 行放在 50.5–61.9 s，Qwen 参考在 6.9–18.1 s。原型的解释是“前 50 s 是调音噪声”，但实测从 5 s 起响度就稳定在约 −24 dBFS，有实际内容。更可能的情况是开头先唱了一遍第 0–2 行，后面又唱了一遍，而 GapDTW 每行只能输出一次。合成样本里的“重复副歌”评测没有发现这个问题。
- 合成金标的局限：样本是原曲做平移、插入、变速、加噪后的结果，音频和原曲几乎相同。真实 Live 是重新演奏的，编曲、音色、节奏都不同，所以合成样本只能证明算法的结构（处理 gap、跳段、串烧）没问题，不能证明精度达标。
- 串烧评测会跳过没找到的歌，不计入误差，所以 0.03 s 偏乐观。

### 3.4 服务端

- Cloudflare 免费额度（官方页面已抓取）：Workers 每天 10 万次请求；D1 每天 500 万行读、10 万行写，共 5 GB；KV 每天只能写 1000 次（不能用作写缓存）；R2 10 GB，每月 100 万次 A 类、1000 万次 B 类操作。
- 估算（每人每天播 30 首）：1k DAU 每天约 3.3–3.9 万次请求，在免费额度内；10k DAU 约 33–39 万次，超出。
- 待核实：调研说“边缘 CDN 缓存命中不计 Worker 请求”。按 Workers 的执行模型，请求路由到 Worker 时会先执行 Worker，所以这一点很可能不成立。要绕开配额，大概得把结果做成静态对象（R2 公开桶或静态资源加 CDN 缓存）。
- 大陆可达性：`*.workers.dev` 不可用、自定义域名可用，这是转述 ITDog 等公开监测数据，没有实测。
- 防投毒最小方案：客户端置信度门槛 + 服务端“两个独立客户端结果一致才标为已验证” + 按设备限流。

## 4. 推荐方案和实施前要补的验证

推荐 ①，并把 ② 作为辅助（MV/原曲搬运的快速识别和粗定位、串烧里原曲段的切分）。③ 在 ① 稳定之后再加，第一版只存本地缓存。

在写实施计划之前，建议先完成下面三项验证（2026-10-28 已完成，结果见 §5）（都还是原型级别，不改 Biu 代码）：

| 编号 | 验证 | 通过标准 |
|---|---|---|
| V1 | 找 3 个以上带人工打轴歌词字幕的**日语 Live**，作为银标（从 Mac 搜，海外 IP 会被拦截） | 找到；找不到就在结论里写明这个缺口 |
| V2 | 让 GapDTW 支持一行歌词在 Live 里出现多次（重复唱、开头先唱一遍），在 sora Live 和银标上复测 | sora 第 0–2 行两次出现都能对上；银标达到 B1'（中位数 ≤ 500 ms，P90 ≤ 1 s） |
| V3 | 在 Electron 里端到端测第一首歌：识别 → B 站搜原曲 → 下载 → `decodeAudioData` 解码 → 对齐，计时并测内存 | Mac 上粗对齐 ≤ 3 s、逐行 ≤ 15 s |

## 5. V1–V3 验证结果（2026-10-28）

### 5.1 结论

| 项 | 结果 | 对第一版的影响 |
|---|---|---|
| V1 日语 Live 银标 | 找到 23 个带人工字幕的 Live，组装了 5 个（第 6 个找不到可靠原曲，跳过） | 有了真实 Live 的精度基线 |
| V2 重复段 | 合成样本解决了（重复类覆盖率从 85–92% 升到 97–98%，没有误报）；真实 Live 上没有变化，Live 里额外多唱的行仍然对不上 | 第一版 Live 以粗对齐为准（已拍板），不阻塞 |
| V3 Electron 端到端 | **耗时达标**：粗对齐热状态中位 2.15 s、冷启动 2.3–2.7 s；逐行 2.5–3.0 s。内存增量中位 468 MB（395–548）；群聊已取消 E1 硬限，此项改为观测 | 解码优化（WebCodecs 等）降为可选优化，不阻塞实施计划 |

### 5.2 V1：银标（`$LYRICS_PROTO/silver/`）

- 搜索：从 Mac 用 wbi 搜索，48 组关键词共检查 1020 个视频，其中 Live 类 664 个、带字幕 65 个（只有 AI 字幕的 39 个）、带人工字幕 26 个。B 站搜索接口请求太密会返回 `v_voucher`（风控），脚本遇到后退避等待。
- 5 个银标：Uru「プロローグ」`BV14f4y1W7jY`、ClariS「reunion」`BV17k4y1z7cT`、fripSide「whitebird」`BV1BQe4eQE85`、「unlimited destiny」`BV1PxWCeEEdj`、kz「DECORATOR」`BV1rdp4efEEV`。都是单曲 Live 切片，不含长 MC 和串烧，所以真实视频的 MC 处理和串烧仍然只有合成样本覆盖。
- 评测口径修正（Claude）：V1b 生成的真值有两个问题，已在 `eval_silver.mjs` 里修正：① 网易云 LRC 一行合了几句、字幕按句打轴时，同一 idx 的连续字幕行只算一次出现；② 副歌等在 LRC 里本来就出现多次的歌词，原先都映射到第一次的 idx，被误判成“Live 重复唱”。改为用前后的唯一行做锚点插值，选最近的 idx。修正前“重复唱条目误差 60–110 s”的结论是评测错误。

修正后的结果（GapDTW 和 V2 新算法结果完全相同）：

| Live | 粗对齐误差 | 逐行中位 / P90 | ≤ 1 s | B1'（中位 ≤ 0.5 s，P90 ≤ 1 s） |
|---|---|---|---|---|
| Uru プロローグ | 0.35 s | 0.34 / 0.70 s | 96% | 达到 |
| fripSide whitebird | 0.39 s | 0.44 / 0.64 s | 100% | 达到 |
| fripSide unlimited destiny | 0.11 s | 0.19 / 1.18 s | 89% | 中位达到，P90 差一点 |
| ClariS reunion | 0.64 s | 0.63 / 4.6 s | 80% | 达不到；Live 额外多唱的 10 条对不上 |
| DECORATOR | 1.89 s | 1.47 / 1.83 s | 14% | 达不到；误差接近固定平移。所选原曲 `BV1mS4y1c7sk` 是 Project DIVA 街机音源，前 3 s 静音，很可能和网易云 LRC 对应的不是同一个版本（推测） |

粗对齐 5 首里 4 首 ≤ 0.65 s，第一版 Live 以粗对齐为准的前提成立。DECORATOR 说明“原曲版本选错”会造成整体偏移，原曲挑选规则要加版本校验（例如原曲时长和网易云时长对上之外，再看 LRC 首句时间附近有没有人声起来）。

### 5.3 V2：重复段（`$LYRICS_PROTO/align/REPORT-V2.md`）

- 新算法 `alignLinesWithRepeats`：主路径仍是 GapDTW，再按段落模板在 Live 上找其他相关峰，相似度 ≥ 0.945 等条件都满足时，才输出额外的一次出现。
- 合成样本：覆盖率 95.0% → 98.3%，中位数 106 ms，P90 204 ms，误报重复为 0；原有 8 类都没有变差。
- 真实 Live：4 个 bench Live 和 5 个银标上，都没有多输出任何一次出现，结果和 GapDTW 完全相同。sora 开头 0–40 s 那遍演唱，行模板的最高相似度只有 0.74–0.80，CENS 特征下和噪声区分不开。
- 309 s 的 Live 在 Mac 上逐行对齐 547 ms，峰值 RSS 169 MB。

### 5.4 V3：Electron 端到端（`$LYRICS_PROTO/v3/REPORT.md`）

- 做法：在 Mac 上把 Biu 1.16.0 复制到 `/tmp`，副本里放测试用的 `Resources/app/`（Electron 38.6.0）。网络在主进程；`decodeAudioData` 在隐藏窗口里跑，对齐在 Web Worker 里跑。12 个案例都跑过，共 9 个全新 user-data-dir 进程、142 次运行。歌名直接用给定值，没有测标题识别。
- 关键路径是原曲链路（中位数）：网易云 182 + 歌词 46 + B 站搜索 380 + view 66 + playurl 80 + 下载 214 ms（约 1.1 MB，低码率 AAC）+ 解码和特征 1077 ms。视频音频链路 1.4 s 就结束了。B 站搜索偶尔变慢，9 次冷启动里有 2 次粗对齐超过 3 s（3.9 s、7.1 s）。
- 只下前 60 s 做粗对齐：几乎不省时间，而且歌曲起点晚于约 45 s 的 Live 会出错，置信度区分不出来。不采用。
- 播放：0 次长任务，119 次 `<audio>` 播放都没有卡顿。
- 内存：增量来自渲染进程里 WebAudio 解码的原生内存（JS 堆峰值只有 9.5 MB），用过之后不回落。实测冷启动首次约 +468 MB。群聊 2026-10-28 19:41 已取消 E1≤300MB 硬限，改为观测；播放不卡（E2）仍必须。WebCodecs 流式解码 / 用完即毁的独立渲染进程仍是可选优化，不阻塞写实施计划与功能代码。
