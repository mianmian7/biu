# 自动歌词 v2 需求

状态：需求已对齐（2026-10-28）；群聊拍板 2026-10-28 18:35 Asia/Singapore，补充 19:41：取消 E1 内存硬限。第一版：V1–V3 已完成；Live 以粗对齐为准、逐行尽力；不做共享缓存；无原曲参考时不自动出词；峰值内存不做硬门槛（观察即可，播放不能卡）。分支 `feat/auto-lyrics-v2`，基于上游 v1.16.0（`7d49920`）。

## 1. 背景

上游已有的歌词能力（新功能复用这些入口）：

- `src/components/lyrics/get-lyrics.ts`：B 站 AI 字幕直接当歌词。
- `src/components/lyrics-search-modal/`：网易云、lrclib 手动搜索。
- `electron/ipc/api/netease-lyric.ts`：网易云歌词接口，已请求 `tv`（翻译）、`rv`（罗马音）。
- `src/components/lyrics/index.tsx`：全局 offset 调整、按播放项缓存。

上一版 gbc-sync（Electron 调 `uv run` 起 Python 后端，用 librosa/synctoolbox 做 CQT+DTW；慢路走 demucs+ASR）已放弃，代码在私有仓库 `mianmian7/biu-archive`。识别规则、网易云接口、罗马音逻辑可以参考，架构不沿用。放弃原因都是实测结果：

| 问题 | 实测 |
|---|---|
| 新机器首次使用 | 现场下载 Python 和依赖约 20 s，macOS 首次加载 scipy 等原生库约 46 s，numba 编译 10–13 s；第一首歌约 107 s 才出歌词 |
| 慢路首次使用 | 下载约 6 GB 模型，耗时 485 s |
| 环境建好后每首新歌 | 5–9 s，其中 AI 识别约 4–4.5 s、下载原曲或视频音频 2–5 s、对齐 1–3 s |
| 稳定性 | 另一台新 Mac 上 `uv` 返回退出码 2，根因未查明 |
| 覆盖 | 只对 TV 版和片段做了优化；Live 效果弱，合集直接拒绝处理 |

## 2. 决策记录

| 维度 | 结论 |
|---|---|
| 用户 | 公开发布，下载即用，零配置 |
| 发布 | **只在 fork `mianmian7/biu` 发布**，不以合入上游为目标；架构不受上游约定限制，但上游代码要能继续合并进来 |
| 平台 | Apple 芯片 Mac、Intel Mac、Windows、Linux |
| 速度 | 两阶段：先显示粗对齐歌词（整体偏移），再自动校准到逐行（指标见 §4） |
| 内容（必须支持） | 官方 MV 和原曲搬运；Live（含 MC、加长间奏、重复副歌、跳唱）；合集和串烧（分 P，以及单 P 内连续多首） |
| 合集和串烧 | **先拿到歌单，再自动定位**。歌单按顺序从分 P 标题、B 站章节（view_points）、简介和置顶评论里的时间轴、AI（可选）获取，都拿不到时让用户选。然后在音频中自动找出每首歌的起止，再逐行对齐。不做无歌单的全自动识别切分 |
| 识别 | 规则优先，AI 可选（不配 key 也能用）。取舍上**尽量自动出结果**，允许少量认错，由用户纠正；认不出时让用户手动选 |
| 语言 | 以日语为主（对齐、翻译、罗马音都必须有）；中文和英文歌要能对齐，不需要罗马音或拼音 |
| 翻译、罗马音 | 优先用歌词源自带的（网易云 tlyric/romalrc）。缺罗马音时本地生成（JS 分词器，词典允许按需下载）；缺翻译时，配了 AI key 就用 AI 补，没配就不显示 |
| 触发 | 视频在音乐区或标题规则命中时，播放开始即在后台自动跑；允许预取下一首；非音乐视频静默跳过；设置里可以关闭 |
| 优先级 | 用户修正（手选歌曲、调整 offset 或行时间）> 共享缓存 > 自动对齐 > B 站 CC/AI 字幕；B 站字幕可以手动切换过去 |
| 用户修正 | 默认匿名回传到共享缓存（只传标识和时间数据），可以关闭 |
| 服务端 | 只用免费额度（例如 Cloudflare Workers+D1/R2）。只上传 bvid/cid、歌曲 ID、偏移和行时间，不上传音频和账号信息。服务不可用或超出额度时退回纯客户端，功能不受影响 |
| 资源 | 对齐在 Worker 或 utility 进程中跑，以单核为主；峰值内存不做硬门槛（观察即可）；播放不能卡顿；长音频优先分块、流式处理 |
| 体积 | 长期想换掉 Electron、整包做到十几 MB，现阶段不做；新功能不能引入 Python 和重型原生依赖 |

## 3. 功能需求

### 3.1 识别

1. 输入：视频标题、分 P 标题、UP 主、简介、标签、分区、章节、置顶评论；可选 AI。
2. 输出：每个分 P 的歌单 `[{title, artist, neteaseId?, start?, end?}]`，附带置信度。
3. 对齐得分要反过来参与识别判定：对齐质量很差时，降级为让用户选歌，不再显示错位的歌词。
4. 手动选歌复用并扩展 `lyrics-search-modal`。串烧要能编辑歌单（增加、删除、调整顺序、修改某一首）。

### 3.2 对齐

1. **粗对齐**：给出整首歌一个全局偏移（串烧给出每首歌的偏移和起止），立即显示歌词。
2. **逐行对齐**：给出每行的起始时间，可以分批更新到界面。
3. Live：MC 和加长间奏期间不显示歌词，重复副歌按实际演唱的次数显示，跳过没唱的行，速度可以和原曲不同。
4. 串烧：在已知歌单下定位每首歌的起止；歌单顺序与实际不一致或有缺漏时要能容错。
5. 输出带置信度，置信度低的行在界面上弱化显示。

### 3.3 歌词、翻译、罗马音

1. 歌词源：网易云为主，lrclib 和 B 站字幕为辅。
2. 翻译和罗马音与原文逐行对应，跟随原文的对齐时间。
3. 罗马音本地生成只覆盖日语。

### 3.4 缓存与共享

1. 本地缓存：识别结果、参考音频特征、对齐结果，按 `bvid+cid` 存储，带算法版本号。
2. 共享缓存：读取优先；本地算出结果或用户修正后异步上传。上传数据要能防滥用，至少做到限流、按多数一致或置信度合并。
3. 服务端不存在时整个链路仍然完整可用。

### 4.2 指标

时间都从按下播放开始计算，基准机器为 Apple 芯片 Mac。“首次”指刚安装、`userData` 和缓存都清空后播放的第一首歌，不能命中共享缓存。

| 编号 | 指标 | 目标 |
|---|---|---|
| A1 | 粗对齐出现时间（首次，单曲、MV、分 P） | P90 ≤ 3 s |
| A2 | 逐行对齐完成时间（首次，单曲、MV、分 P） | P90 ≤ 15 s |
| A3 | 逐行对齐完成时间（Live；串烧按每首歌计） | P90 ≤ 30 s；串烧的后续歌曲在播放到之前完成 |
| A4 | 共享缓存命中时的出歌词时间 | P90 ≤ 2 s（逐行） |
| B1 | 逐行起点误差（金标，§4.3） | 中位数 ≤ 300 ms，P90 ≤ 700 ms |
| B1' | 逐行起点误差（银标，§4.3） | 中位数 ≤ 500 ms，P90 ≤ 1 s（银标自身有误差，所以放宽） |
| B2 | 粗对齐全局偏移误差（原曲、MV） | ≤ 1 s |
| B3 | 已演唱行的覆盖率 | ≥ 90% |
| B4 | MC 和间奏期间误显示的歌词 | 每段 MC 不超过 1 行 |
| B5 | 串烧每首歌的起止误差 | ≤ 3 s；歌曲判对率 ≥ 90% |
| C1 | 识别：不配 AI，应识别样本的自动命中率 | ≥ 80% |
| C2 | 识别：不配 AI，认错率 | ≤ 8% |
| C3 | 识别：配 AI 后的自动命中率 | ≥ 90%（1.16.2 的“新逻辑”基线为 47/60） |
| C4 | 非音乐或应拒绝样本的误触发率 | ≤ 5% |
| D1 | 翻译：歌词源有翻译时的显示率 | 100% |
| D2 | 罗马音：日语歌的显示率 | 100%（源自带或本地生成） |
| E1 | 后台对齐期间的峰值内存增量 | **不做硬门槛**（群聊 2026-10-28 19:41 取消）；记录观测值即可；仍要求 E2 播放不卡 |
| E2 | 后台对齐期间的播放卡顿 | 0 次；渲染进程没有超过 200 ms 的长任务 |
| E3 | 安装包体积增量（罗马音词典按需下载时不计入） | ≤ 25 MB |
| E4 | 首次使用时必须下载的东西 | 只有参考音频和歌词；不下载运行时、模型或依赖 |
| F1 | 平台 | Apple 芯片 Mac、Windows（pc）、Linux（wsl）真机跑完 A–E；Intel Mac 用 GitHub Actions 的 Intel macOS runner 打包，并跑无头对齐冒烟测试 |
| F2 | 服务端不可用 | 断网或关闭共享缓存时 A1–A3、B 组指标不退化 |
| F3 | 服务端成本 | 按 1k / 10k DAU 估算，都在免费额度内，否则要给出限流或降级方案 |

### 4.3 真值来源（不需要人工）

| 档 | 来源 | 精度 | 覆盖 |
|---|---|---|---|
| 金标（合成） | 用 `studio/` 原曲和 `lyrics/*.lines.json` 的原曲行时间做已知变换：整体平移、插入 30–120 s 的 MC（人声或现场噪声）、加长间奏、重复副歌、删除段落、±5% 变速、混入人群噪声和混响、多首拼接成串烧。行时间通过变换直接算出 | 精确，误差只来自原曲 LRC 本身 | B1、B3、B4、B5 的主要依据 |
| 银标（真实视频） | 在 B 站找带人工打轴歌词字幕的 Live、串烧视频（UP 主上传的 CC 字幕，字幕作者不是 AI），以字幕的行起点为参考 | 约 ±200–500 ms | 真实 Live 和串烧的 B1'、B5 |
| 一致性（无真值） | 现有 4 个 Live：两种独立方法（新方案和 `runs/` 里的 M4/Qwen 结果）在 1 s 内一致的行占比，以及新方案的置信度分布 | 只用来发现问题，不作为通过条件 | 回归对比 |

原曲 LRC 的质量要先抽查：网易云 LRC 与原曲音频的整体偏移如果超过 300 ms，先校正，或者把这首歌剔出金标。

## 5. 不做

- 不做无歌单的全自动串烧识别。
- 不做中文拼音和韩语罗马字。
- 不引入 Python、PyTorch 或需要现场下载的大模型。
- 现阶段不更换 Electron。
- 不上传音频，不做服务端计算。

## 6. 待定 / 已收口

- 原曲参考音频：方案调研倾向 **B 站搜 CD 搬运**（网易云 VIP 匿名不可用）。**没有可用原曲时不自动出词**（2026-10-28 拍板），沿用手动搜索。
- 银标视频能找到多少：V1 验证项。若带人工打轴字幕的 Live/串烧少于 3 个，缺口写进验证结论；因第一版 Live 不以逐行银标为硬门槛，不阻塞进入实施，但仍建议尽量补。
